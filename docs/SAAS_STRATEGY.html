Platform strategy

From one server to a SaaS platform

How Payobook grows from a single Odoo 19 instance on Lightsail into a multi-client SaaS — with real data isolation, one shared codebase, and a scaling path you only pay for when you need it.

Target: 2–10 clients, 12–18 months client.payobook.com per tenant One database per client One shared codebase
The strategy in one sentence: adopt the model Odoo S.A. runs its own SaaS on — one codebase, one Odoo service, one wildcard domain, and a separate PostgreSQL database per client — stay on the current Lightsail box until clearly defined triggers fire, then move the database tier out first and the compute tier second. No new ports, no per-client servers, no rewrite.
Decisions

Your questions, answered

Each of the ideas you raised, judged against what production SaaS platforms actually do.

Yes — do this

Subdomains per client

acme.payobook.com, vinh.payobook.com — exactly right. Subdomain-per-tenant is the standard for B2B SaaS (Slack, Shopify, Zendesk, Odoo Online all do it). One wildcard DNS record *.payobook.com and one wildcard TLS certificate cover every client you will ever add — onboarding a client requires zero DNS work.

Odoo supports this natively: with dbfilter = ^%d$ the subdomain automatically selects the client's database. No custom routing code.

Yes — with guardrails

Same codebase, same server

Correct for 2–10 clients. Pros: deploy once and every client benefits, one server to secure and patch, lowest possible cost per client, one monitoring surface.

Cons you must manage: a bad deploy or a heavy job affects everyone (shared blast radius), and all clients ride the same Odoo version. Guardrails: test on a staging copy before every rollout, keep client-specific modules installed only in that client's database, and keep a documented escape hatch — a demanding client can graduate to their own container later.

No — not needed

Different ports per domain

Ports are the wrong tool. HTTP routing is done by hostname (the Host header), not by port. nginx listens on 443 for all subdomains and proxies every one of them to the same Odoo backend on 8069; Odoo picks the right database from the hostname.

Per-client ports would break clean HTTPS URLs, multiply certificates and firewall rules, and add zero isolation. Everything stays on 443 outside and 8069 (plus the websocket/gevent port) inside.

Fine now — plan the exit

Lightsail performance

Lightsail comfortably carries 2–10 tenants — bundles now reach large sizes, and payroll traffic is spiky-but-predictable (month-end), not consumer-scale.

Its real limits: no autoscaling, everything on one box, and app + database compete for the same RAM and disk I/O. The strategy is trigger-based migration: precise, measurable conditions (in section 7) that tell you when to move the database out, and later the compute. Don't migrate pre-emptively — that's paying for problems you don't have yet.

Architecture

Target architecture

The native Odoo SaaS pattern: shared code and process, isolated data. This is what Odoo S.A. runs odoo.com's own hosted offering on, and what most independent Odoo SaaS providers use at this scale.

How a request flows

  1. A user opens acme.payobook.com. The wildcard DNS record resolves it to your server.
  2. nginx accepts it on 443 with the wildcard certificate and proxies it to Odoo on 8069 — the same backend for every client. The Host header travels with the request.
  3. Odoo's dbfilter = ^%d$ matches the first label of the hostname (acme) against database names and opens the acme registry. The user sees only that database — they cannot reach, list, or even learn of any other tenant.
  4. The apex (payobook.com) keeps its own nginx server block which pins the existing Payobook19v2 database via the X-Odoo-dbfilter header — so the marketing site and demo world continue unchanged without renaming anything.

The key configuration (for later — Phase 1)

# /etc/odoo-server.conf
db_name =                  # remove the pin — the filter chooses per request
dbfilter = ^%d$            # acme.payobook.com -> database "acme"
list_db = False            # nobody can enumerate or manage databases via the web
proxy_mode = True          # already set

# nginx: one extra server block
server {
    listen 443 ssl;
    server_name *.payobook.com;          # every current and future client
    # wildcard cert via DNS-01 challenge
    location / { proxy_pass http://127.0.0.1:8069; ... }
    location /websocket { ... }          # same upgrade headers as today
}
server {
    listen 443 ssl;
    server_name payobook.com;            # apex stays on the existing DB
    proxy_set_header X-Odoo-dbfilter ^Payobook19v2$;
    ...
}

Naming rule from day one: a client's database name must exactly equal their subdomain label (acme DB ↔ acme.payobook.com), lowercase, no spaces. This one convention is what makes routing, provisioning, backups and the upgrade loop all scriptable with zero lookup tables.

The core decision

Tenancy models compared

Four ways the industry hosts multiple clients, and why database-per-tenant wins for payroll at your scale.

Model Data isolation Cost / client Ops burden Verdict for Payobook

Container per tenant
Docker: each client gets an Odoo container + DB		 Strong+ — process & resource isolation too Medium Medium–high (orchestration, registry, per-container upgrades) Later. The documented Phase-4 evolution — worth it beyond ~10–20 tenants or for a client demanding dedicated resources. Premature today.
VM / server per tenant
A separate Lightsail box per client		 Strongest Highest Highest — N servers to patch, monitor, certify Rejected as default. This is your existing on-prem/enterprise track, priced accordingly — not the SaaS baseline.

Why this is also what the state of the art does

Modern SaaS vocabulary (the AWS SaaS Lens) calls these the pool (shared everything), silo (dedicated everything) and bridge (shared compute, isolated data) models. Consumer-scale products (Slack, Notion) pool aggressively because they built row-level isolation into their product from day one and operate at millions of tenants. B2B systems that hold regulated or high-sensitivity data — payroll, accounting, health — overwhelmingly choose the bridge or silo model. Odoo's own hosted SaaS is bridge: shared application servers, one database per customer. You inherit a decade of that platform's design decisions (dbfilter, per-DB registries, per-DB filestores, per-DB module installs) for free by following the same shape.

Non-negotiables

Security & data isolation

Payroll is among the most sensitive data classes a business holds. These controls are the platform's baseline, not enhancements.

Hard database boundaryEach client's data lives in its own PostgreSQL database and its own filestore directory. No SQL query, ORM call or export can cross tenants — isolation is structural, not rule-based.
Database manager disabledlist_db = False hides every database-listing and create/duplicate/drop endpoint from the web. Provisioning happens only over SSH.
Strong master passwordadmin_passwd rotated to a long random secret and stored in a password manager — it protects every tenant at once.

Shared code, private features

Custom code per client — without breaking the others

Some clients will need their own modules. The trick is that a shared addons path is safe in Odoo: each database only loads the modules installed in it. Custom code sits beside core code on disk, but only exists inside the paying client's world.

Two-tier addons layout

/odoo/custom/addons/
├── payobook-core/          # the product — every pb_*, biz_* module; all tenants
└── payobook-custom/
    ├── acme/               #   xc_acme_overtime_rules, xc_acme_bank_export ...
    └── vinh/               #   xc_vinh_union_levy ...
  • Naming: client modules are prefixed xc_<client>_* — grep-able, unmistakable in any module list, and impossible to confuse with the product.
  • The one hard rule: client modules are installed only in that client's database. Odoo builds a separate registry per database, so an uninstalled module is inert — code on disk that a tenant never executes.
  • Never fork core for one client. A client need is either (a) configuration — Payobook's formula-config system already covers most payroll variance, (b) a generic feature worth adding to payobook-core for everyone, or (c) a true one-off that becomes an xc_ module inheriting core. Decide explicitly which of the three it is, every time.
  • Rollout ritual: restore last night's backup of that client's DB as acme_staging, install/upgrade there, smoke-test the payroll run, then apply to production in a maintenance window. Other tenants are untouched because nothing was installed in their databases.

The escape hatch (write it into the client contract tier): when a client's custom surface grows large — many modules, integration daemons, strict SLA, "we need our own version" — they graduate to a dedicated container or box at a dedicated-infrastructure price. The shared platform never bends its rules for one tenant; the tenant moves instead. This is exactly how Odoo.sh and every mature SaaS handles the outlier client.

Capacity

Performance & scaling on Lightsail

One well-tuned box carries this stage comfortably. What matters is knowing the tuning knobs, the honest ceiling, and the exact tripwires that trigger each migration step.

Tuning the single box (do once, in Phase 0)

  • Worker mode: confirm workers is set (rule of thumb: 2 × vCPU + 1, each worker budgeting roughly 300–800 MB for payroll workloads) and that the websocket/longpolling port (8072, gevent) is the one nginx's /websocket block proxies to. Multi-tenant traffic on a single threaded process is the first thing that would hurt.
  • Cron isolation: keep max_cron_threads = 1 so scheduled jobs (one tenant's payrun) can never occupy all workers and starve interactive users of other tenants.
  • Connections: db_maxconn × workers must stay under Postgres max_connections; give Postgres ~25% of RAM as shared_buffers.
  • The known noisy neighbour: your formula-engine payruns over thousands of employees are exactly the heavy job that can starve other tenants. Mitigate by scheduling client payruns off-peak and keeping batch compute chunked (the wizard already computes in batches) — and treat "a payrun visibly slowed another tenant" as a formal migration trigger, below.

Migration triggers — move only when a tripwire fires

Tripwire (measured, not felt)ActionEffort
Sustained CPU > 70% or RAM pressure outside payrun windows Resize to a larger Lightsail bundle (snapshot → relaunch). Vertical scaling is the cheapest move and buys the most headroom per hour spent. Hours
One tenant's payrun measurably slows another tenant, more than once Split the database tier out: managed PostgreSQL (Lightsail managed DB or RDS) or a second instance. App and DB stop competing for RAM/disk; DB gains its own backups, metrics and failover option. 1–2 days
Backup/restore windows getting long, or disk I/O saturating at month-end Same as above — the database tier moves first. This is the industry-standard first split for exactly this reason. 1–2 days
Compute ceiling on the largest sensible bundle, or you need autoscaling / private subnets Move compute to EC2 (or containers on ECS). Lightsail has no autoscaling and limited networking — this is its genuine end of the road. Days
> ~10–20 tenants, or a client contractually requires dedicated resources Containerize: one Odoo container per tenant (or per tenant-group), orchestrated. Strong process isolation, per-tenant versions and resource caps become possible. Weeks

Sequencing matters: database out first, compute second, containers last. Each step is independently useful, reversible in planning, and none requires redesigning the application — because the tenancy model (DB-per-tenant) was chosen to survive all three moves unchanged.

Running it

Operations: provisioning, upgrades, backups

At 2–10 tenants the right tooling is a small set of boring, reliable scripts — not a control-panel product.

Onboarding a client (target: under 30 minutes, scripted)

  1. Golden template: maintain one payobook_template database — Payobook fully installed and configured, zero client data, outgoing mail and crons neutralized.
  2. Clone it: createdb acme -T payobook_template + copy the template filestore to filestore/acme. (DB name = subdomain, per the naming rule.)
  3. Personalize: set company details, web.base.url = https://acme.payobook.com (frozen), create the client admin user, enable crons and mail.
  4. Verify: open https://acme.payobook.com — wildcard DNS and TLS already cover it; log in, run the smoke checklist.
  5. Record it: one row in the tenant register (client, subdomain/DB, plan, go-live date, custom modules, contacts).

Deploying code to N tenants

Your existing proven deploy ritual (staged rsync → stop → detached systemd-run upgrade with a sentinel file → start → verify) generalizes directly: rsync once — the codebase is shared — then loop the -u upgrade step over each tenant database before restarting. Two additions become mandatory at N > 1:

  • Staging first, always: restore a production tenant's backup as a staging DB, run the full upgrade + a payroll smoke test there before touching production tenants.
  • Maintenance windows: announce a standing window (e.g. a weekday 21:00 slot) in client contracts. At this scale upgrades take minutes per DB; the window is about expectations, not duration.

Backups

  • Nightly per-tenant pg_dump + filestore tar, encrypted, uploaded off-box; 30–90 day retention per contract tier.
  • Weekly Lightsail snapshot of the whole instance (fast disaster recovery of the box itself).
  • Quarterly restore drill: restore one tenant into staging, open it, run a payslip. Log that it happened.

Monitoring (minimum viable)

  • Uptime checks on the apex plus every tenant subdomain (any external monitor; a check per tenant is one line).
  • Lightsail metric alarms: CPU, RAM (via agent), disk fill.
  • A daily glance-able digest: last night's backup sizes per tenant + error-count grep of the Odoo log.
Execution

Phased roadmap

Five phases, each independently shippable, each leaving the platform strictly better. Phases 0–2 are the SaaS foundation; 3 monetizes customization; 4 is the pre-planned growth path you execute only when triggers fire.

0

Harden the current box

~2–3 days · before any tenant

Make the single-tenant server safe enough to carry other people's payroll. Every item here protects the existing system too — zero risk of regression.

Steps

  • Set list_db = False; rotate admin_passwd to a vault-stored secret
  • Configure SMTP relay + SPF/DKIM/DMARC (also unblocks the existing demo signup emails)
  • Audit workers/gevent port vs the nginx websocket block; set max_cron_threads = 1
  • Stand up nightly encrypted pg_dump + filestore backup to object storage; weekly instance snapshot
  • nginx rate-limit on /web/login; fail2ban

Verify

  • Database manager URLs return 404/refused from the web
  • A test mail arrives in Gmail inbox (not spam)
  • A backup file restores cleanly on a scratch DB
  • Login rate-limit trips on a scripted burst
1

Multi-tenant plumbing + pilot tenant

~2–4 days

Wildcard domain, dbfilter routing, and a first real tenant database — proving isolation end-to-end while the apex site keeps running unchanged.

Steps

  • Add DNS *.payobook.com A record (and www while at it)
  • Issue wildcard Let's Encrypt cert via DNS-01 challenge (automate renewal with the DNS provider's API)
  • Add the wildcard nginx server block; pin the apex block to Payobook19v2 via X-Odoo-dbfilter
  • Switch odoo-server.conf: drop db_name pin, set dbfilter = ^%d$
  • Create a pilot tenant DB (e.g. pilot) and run a full payroll cycle in it

Risks & verify

  • Apex regression is the main risk — verify payobook.com, /demo signup, and the demo world before and after
  • pilot.payobook.com reaches only the pilot DB; apex reaches only Payobook19v2
  • A wrong subdomain (nothere.payobook.com) fails cleanly, leaking nothing
  • Websocket bus works on both hosts (no "real-time connection lost")
2

Tenant lifecycle automation

~3–5 days

Turn onboarding, backup and upgrade into scripts so a new client is routine, not a project.

Steps

  • Build the payobook_template golden database (installed, configured, neutralized, no data)
  • tenant-new.sh: clone template → filestore → base URL → admin user → smoke check
  • tenant-backup.sh: per-tenant dump/archive loop (called nightly)
  • Generalize the deploy ritual: per-DB -u loop with a sentinel per tenant
  • Start the tenant register; write tenant-offboard.sh (export, drop, log)

Verify

  • Provision a throwaway tenant end-to-end in < 30 minutes, then offboard it cleanly
  • A code deploy upgrades template + all tenants, and each subdomain passes its smoke check
3

Custom-code delivery process

~2–3 days + per-client work

Ship the first client-specific module under the two-tier addons layout, establishing the pattern every later customization follows.

Steps

  • Create payobook-custom/<client>/ in the addons path; adopt the xc_<client>_* naming rule
  • Write the config-vs-core-vs-custom decision rule into the engineering doc
  • First custom module: staging-copy test → window → install in that tenant only
  • Price customization + define the dedicated-infrastructure graduation tier commercially

Verify

  • The module exists on disk for all, is installed in exactly one DB, and other tenants show zero behavior change
  • A core deploy after the custom install passes on all tenants (no hidden coupling)
4

Scale-out — executed on triggers only

When tripwires fire (section 7)

The pre-planned growth path. Nothing here is built in advance; each move is a known, costed play executed when its measured trigger fires.

The plays, in order

  • Bigger Lightsail bundle (vertical)
  • Database tier out to managed PostgreSQL / RDS
  • Compute to EC2/containers when the box's CPU is the limit
  • Container-per-tenant orchestration beyond ~10–20 tenants

Why it's safe to defer

  • DB-per-tenant survives every one of these moves unchanged — databases migrate one at a time, subdomains never change
  • Nothing in Phases 0–3 has to be redone
Anticipated questions

FAQ

Can a client use their own domain, like payroll.acme.com?

Yes, as a premium option. They add a CNAME payroll.acme.com → acme.payobook.com; you issue a certificate for that hostname (HTTP-01 challenge works fine for single names) and add a small nginx server block that pins their database via X-Odoo-dbfilter ^acme$. Keep it a paid tier — each custom domain is a certificate and a config block you now own.

How do Odoo version upgrades (19 → 20) work with many tenants?

The same as one tenant, times N — which is exactly why the tenant count on a shared platform should grow faster than the version count. Migrate the template first, then tenants one at a time (each is an independent database), staging-tested each. Until a migration completes you can run two Odoo services side by side (old and new version) and point each tenant's nginx block at the right one — a per-tenant cutover with instant rollback.

What happens to the demo world and the marketing site?

Nothing — that's deliberate. The apex keeps serving pb_website and the shared demo database. Strategically it becomes the top of the funnel: visitor → demo signup (existing pb_demo_portal) → guided trial → sales conversation → tenant-new.sh. The Phase-0 SMTP fix is what makes the existing signup flow actually deliver its emails.

Why not one big multi-company database? Odoo supports companies natively.

Multi-company is for one organization with several legal entities — shared users, shared chart of accounts patterns, cross-company flows. Between unrelated businesses it means their salary data is separated only by ORM record rules; one misconfigured rule or one sudo() in any module leaks payroll across clients. It also makes per-client backup, restore, export and deletion impossible. The hard Postgres boundary costs nothing at your scale and removes the entire risk class.

Does every new client make the server slower?

Marginally, and mostly in RAM: each active tenant's registry and cache occupy worker memory, and its users occupy worker time. Payroll usage is bursty (month-end) and small-N tenants mostly idle. The Phase-0 tuning plus the section-7 tripwires are the honest answer: measure, and act only when a threshold is actually crossed.

Should provisioning be self-service (client signs up, instance appears)?

Not yet. Fully automated self-service provisioning is what odoo.com and SaaS kits sell, but at 2–10 B2B payroll clients every onboarding involves data import, formula configuration and training anyway — a scripted 30-minute manual step is not the bottleneck, and skipping the control-panel build saves weeks. Revisit if trial volume ever makes sales-touch onboarding the constraint.
