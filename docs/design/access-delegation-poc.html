The product direction

Use Studio as the home. Borrow the best of the other two.

Make Guided Setup the “New role” journey and People Passport the “See effective access” view. They should share one permission model so the simple view and the detailed view always agree.

Evidence before redesign

Keep the foundations. Make the boundaries visible.

Reviewed the live Payobook Access screen and New role composer, plus the repository’s Access templates, role editor, ability / profile models, assignments and delegation logic. This is a UI and code review, not a production security audit. No live permissions were changed.

What is already working

01
Human-readable roles and abilities

Existing roles bundle permission groups into business language. Retain the ability descriptions as helpful detail.

02
People, roles, screens and hand-overs

The existing lenses and “See it as” give useful context. The current preview describes access; it is not an impersonation login.

03
Change provenance and safe hand-back

The code tracks role assignments, revisions and change history. Delegations record their grants and preserve independent access when they end.

What should improve

↗
Action levels are buried in sentences

The composer offers broad ability checkboxes. View, create, edit, delete, approve and export deserve separate visible controls.

↗
Scope and fields need their own editor

No generic own / team / company record-scope builder or field access editor was visible in the reviewed Access flow. Existing backend rules may still restrict access elsewhere.

↗
The first screen asks too much at once

A long role list and many header actions compete for attention. Put everyday editing first; move history, expiry cleanup and exports into their relevant views.

These concepts add a proposed policy-editing layer. Independent CRUD levels, per-operation record scopes, dynamic field write permissions, masking and exact-time expiry require backend implementation and verification. They cannot be delivered safely by hiding buttons or changing form attributes alone.

How the proposed permission model should behave

Profile describes the account baseline (Employee, Staff or External). Role is a reusable job bundle. Rule limits an action’s records. Field policy controls visibility, editing and input on create. Delegation is a bounded temporary assignment. Avoid making users maintain both a “profile” and a “role” that duplicate the same job permissions. The current pb.role.profile model already means a role; migration should preserve that identity.

Resolve existing groups, direct grants, roles and active delegations first. Existing Odoo ACL grants are additive, group record rules combine by union, and global rules constrain them. “None” in one role therefore means “this role does not grant it”; another source can still allow it. Show that source, and never promise that a simple unchecked box is a universal denial.

Company boundaries remain mandatory. Validate ownership and company on creation and on updates that move a record. “Own” needs an explicit mapping per resource: employee relation, expense claimant, or another business owner; creation author is a different condition. Unsupported mappings should block publication. “Team” in this POC means self plus direct reports, never an assumed whole hierarchy.

Enforce field restrictions on the server across forms, lists, exports, reports, imports, API calls and attachments. Native field group restrictions can protect field access; per-role read-versus-write, per-record fields and masking need additional enforcement. A required hidden field needs a safe server default or must make creation unavailable. Keep workflow approval, export, mass update and bank-file generation separate from ordinary editing.

Delegation must stay within the lender’s effective grant and company boundary, expire at an explicit timezone-aware instant, prevent onward lending by default and preserve independent access. Review high-impact grants and conflicts such as preparing and approving the same payroll. Compute expiry at authorization time as well as scheduling cleanup; the current date-based expiry behavior should remain clearly documented until upgraded.

Reference: Odoo 19 · Security model. Simulator logic in this document is intentionally small and uses fictional records; it is not the Odoo permission evaluator.

Recommendation & choice

Choose Studio for the main experience.

It improves the existing role-based product with the least conceptual disruption. It also makes the largest capability gap—actions, records and fields—visible in one workspace. The comparison below is a design judgment, not measured usability data.

First

Clarity and granular controls

Inventory current effective grants. Add the supported resource catalogue, action matrix, scope presets and Hidden / View / Edit fields. Preserve existing assignments and audit history.

Next

Rules and trustworthy preview

Add validated no-code conditions, effective-access explanations, before / after impact, required-field checks and cross-surface security tests.

Then

Governance without clutter

Add exact-time delegation, approval policies, periodic access reviews, role comparison, bulk assignment, stale-access review and time-bound exception requests.
