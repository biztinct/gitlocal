Assigned access is different from equivalent access

The current count of 185 comes from users who have every permission in the Demo bundle. It does not prove that all 185 were explicitly assigned Demo. Expanding the bundle can make people disappear from that count without changing their login permissions.

The new People view will show Assigned permanently, Temporary grant and Equivalent permissions separately. Only actual assignments follow role changes automatically.

Migration uses grant history where reliable. Existing group memberships with unknown provenance stay as legacy access, with a reconciliation list for the administrator. No bulk role assignment is inferred from the holder count alone.

Verified gaps and proposed fixes

Live Chrome verified the read-only form and misleading edit entry point. The remaining findings come from repository code; failure scenarios still need implementation tests.

1 · “Edit roles” opens a read-only form

Evidence: the live QA Test session can see “Edit the list of roles”, but the Demo form has no editable abilities or Edit control. The board permits registered application managers; profile write ACLs cover only Access team.

Fix: a dedicated editor behind one server-authorized management policy. Show “View role” and a clear reason to readers; show Edit, Save and Discard to authorized editors. Route raw form writes through the same guarded service without globally broadening ACLs.

Sources: biz_access/security/ir.model.access.csv; pb_access_facade.py::_require_manage; pb_vendor_access/models/vendor_common.py; access_board.xml.

2 · Editing a role does not update existing users

Evidence: ability edits recompute the role’s group bundle. Grant adds groups to a user at that moment; no profile write synchronizes assignments.

Fix: persist user–role assignments. Publishing a role version reconciles every active assignment automatically, including additions and removals. Never require regranting the role.

Sources: pb_role_profile.py::_compute_group_ids; pb_access_facade.py::grant / grant_many.

3 · Holder counts confuse assignment with matching permissions

Evidence: _holder_users intersects permission-group members. A bundle change changes who “holds” the role even before any user permissions change.

Fix: stable assigned-user counts, separate effective-access matches, and explicit assignment origin. Review the 185 legacy matches before migrating them.

Source: pb_role_profile.py::_holder_users.

4 · Screens manages main entries, not all People tabs

Evidence: Screens lists parent sidebar items; child entries appear as non-editable labels. People’s Records, Pay and Plan tabs are declared by individual modules and have their own gates.

Fix: one navigable screen catalogue: People → Employees → Contracts; People → Records; People → Pay; People → Plan. Expose supported actions per surface and preview the whole path.

Sources: access_board.xml; pb_access_facade.py::screens_board; pb_people_hub / pb_records / pb_pay palette registrations.

5 · Showing a menu does not grant backend access

Evidence: adding Demo to People’s sidebar gate does not satisfy Records’ _may_read check. Giving HR or Payroll Officer just to show Records also grants broader access.

Fix: dedicated Records viewing/editing capabilities, enforced in the facade and model ACLs. Existing HR and payroll roles retain their current entitlements. The catalogue reports any permission that also opens other screens.

Sources: pb_records/models/pb_records_desk.py::_may_read / _may_write; pb_records/security/ir.model.access.csv.

6 · Overlapping grants can lose access when a loan ends

Evidence: delegation snapshots only newly added groups; _end removes those direct groups without testing all remaining grant sources. A second loan can add nothing because the first already supplied the group.

Fix: record entitlement sources even when no membership was added. Recompute the union of active roles, direct grants and loans on expiry/revocation. Snapshot loans to their approved role version; an edit never silently expands a loan. Narrowing a role caps old loans immediately.

Source: pb_access_delegation.py::_activate_one / _end.

7 · Other open sessions can show yesterday’s permissions

Evidence: hub gates and user group checks are cached for a page load. Sidebar writes refresh the editor’s rail, not every affected user’s open session.

Fix: access revision per user, server cache invalidation and an after-commit event to affected sessions. Refetch tabs, palette and menus; close a revoked screen with an explanation. Backend checks always use current authorization.

Sources: pb_hub/static/src/js/hub_gates.js; access_board.js::afterScreenWrite.

8 · Preview can overstate access when a gate cannot resolve

Evidence: resolveLensAccess marks failed group lookups true; a failed probe keeps the earlier allowed value. surface_access treats all-unresolved groups as open. These are UI/preview gaps; backend facades still enforce access.

Fix: distinguish Allowed, Denied, Unavailable and Unknown. Unknown never presents an enabled door. Use server-owned surface definitions and backend checks rather than treating client-supplied group lists as authorization.

Sources: hub_gates.js::resolveLensAccess; pb_access_facade.py::surface_access.

9 · Removing a role may leave older access paths in place

Evidence: sidebar permissions and role gates are combined with OR. Older groups can still open a door after its role gate is removed.

Fix: show “Access also comes from…” and distinguish a role contribution from effective user access. Convert legacy gates only after an impact review; never clear unknown permissions automatically.

Source: biz_access/models/pb_sidebar_item_ext.py::_state_for.

10 · Upgrades can reapply Demo wiring

Evidence: pb_demo rewires model access and adds Demo to gated sidebar items on upgrades. Some sidebar data also replaces group lists.

Fix: separate shipped defaults from administrator overrides. Apply defaults only where no override exists; explicit migrations show a diff. Ensure an upgrade never silently broadens a customized role or restores a removed gate.

Sources: pb_demo/models/demo_sidebar_access.py; pb_demo/hooks.py::post_init_demo; pb_sidebar data.

11 · Raw role writes bypass lifecycle checks

Evidence: the board’s archive method checks holders and loans, but the raw form exposes Active. The model has no equivalent lifecycle guard or role-version history.

Fix: all edit, archive, ability-change and API paths go through the same validation. Archive blocks while assignments or grants remain; provide an explicit reviewed revoke-and-archive flow. Audit before/after versions and user outcomes.

Sources: pb_access_facade.py::archive_role; biz_access/views/access_views.xml; pb_role_profile.py.

12 · Feature entitlement and data scope are separate blockers

Evidence: People Plan has a feature gate; models enforce record rules and company scope beyond menu membership.

Fix: show the actual reason a screen is unavailable: module absent, company feature off, missing ability, parent inaccessible or data scope. Role editing cannot expand company access or enable a commercial feature implicitly.

Sources: pb_people_hub/static/src/js/people_hub.js; pb_hub/static/src/js/hub_gates.js.

13 · No combined change review or conflict protection

Evidence: menu gate clicks save immediately; the role form has no all-user impact diff or revision check.

Fix: draft → before/after review → one atomic publish. Require a reason; compare the role revision under a lock and reject stale edits. High-impact abilities show their actual actions. Reverting a version is a new audited change with a fresh impact calculation.

Sources: access_board.js::_writeGates; biz_access/views/access_views.xml.

One publish operation

1. Authorize the editor and verify the expected role revision.
2. Validate capabilities, forbidden administrator closure, affected surfaces, company scope and active grants.
3. Lock affected role/assignment records in a stable order; compute before/after access for every assigned user.
4. Write the role version, entitlement sources, group projection and audit entry in one database transaction.
5. Commit, invalidate authorization caches, then notify affected sessions to refresh. Report the actual users changed and access retained from other sources.

If any permission write fails, roll back the entire change. Large cohorts need a staged version with an atomic activation boundary; never claim success while only part of the cohort is updated.

Proposed data model

RecordResponsibility
Role + immutable role versionStable identity, named abilities, version, actor, timestamp, reason and before/after values.
User–role assignmentUser, role, status, permanent/temporary source, effective dates and database/company scope. Survives role edits.
Entitlement sourceTracks each role, direct permission, baseline or delegation contribution independently, including duplicate contributions.
Surface / capability catalogueServer-owned hierarchy of menus, tabs and actions; backend requirements and feature/module availability.
Access revision + change auditPer-user refresh revision; resulting additions, removals, retained access, skipped inactive users and migration decisions.

Effective permissions = baseline + explicit direct grants + all active role assignments + valid temporary grants, followed by company and record-rule restrictions. Odoo groups remain the enforcement projection; inferred membership is never the assignment source of truth.

Observe writes to user/group membership from provisioning, imports and administration. Preserve unknown legacy sources and flag drift; do not delete them. The reconciler marks its own writes so they cannot be mistaken for new direct grants. Reconcile implied-group closure without dropping permissions needed by another source.

Odoo group membership is database-wide. Company-scoped assignments need corresponding server capability checks and record rules; a company field on an assignment cannot enforce that scope by itself. Preserve allowed companies and existing global restrictions.

Rollout order

  1. Fix editor authorization and expose clear edit/view modes; deliver the screen catalogue and draft preview.
  2. Inventory current grants and group membership. Seed confirmed assignments from reliable active history; review ambiguous matches. Run reconciliation in shadow mode and compare with current access.
  3. Implement source tracking, atomic role publishing, safe removals and delegation expiry. Route all writers through the same model/service guards.
  4. Add narrow Records capabilities, shared gate definitions, feature explanations, live refresh, audit and upgrade-preserved overrides.
  5. Exercise on a database clone, then deploy the latest combined repository state to every agreed environment/database after the deployment inventory is verified.

This is a design deliverable. Runtime implementation, data migration and application deployment are outside this turn’s requested scope.

Acceptance checks before implementation is complete

  • An authorized application manager edits Demo; a reader sees a reason and cannot write through UI, RPC or the raw form.
  • Adding/removing an ability updates every active assigned user without regranting; inactive assignments follow the current version on reactivation.
  • Counts remain stable across bundle edits. A user with equivalent permissions is not silently assigned the role.
  • Shared roles, two overlapping loans, loan-to-permanent conversion, implied permissions and direct grants retain valid access when another source ends.
  • Menus, tabs, palette, preview and backend agree. Direct URLs and exports enforce current permissions and company scope.
  • Missing groups/probes show Unknown or Unavailable; a feature switch cannot widen data access.
  • Concurrent edits reject stale versions; injected failure rolls back role, all users and audit together. Version reversion gets a new audit entry.
  • Module upgrades preserve overrides; seeded defaults cannot silently restore removed access.
  • Chrome end-to-end checks cover editor, Demo login and a second already-open session. Clean up only screenshots/PNGs created by those tests.
  • Commit scoped changes, re-check concurrent branch work, deploy combined state and report all target databases and deployed test results.

Prototype controls use local example data. No production roles, users, permissions or feature settings are modified.
