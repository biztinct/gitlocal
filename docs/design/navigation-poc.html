The recommendation

Make B the Payobook standard.

A small, stable location trail plus an explicit return destination gives payroll specialists and occasional users the context they need. Show both only when they lead somewhere different.

Use A for deeply nested setup. Reserve C for a future high-volume review workspace, after validating the need with payroll operators.

01 · Location stays stable

Payroll → Pay runs → October run. Entering from Inbox never changes the record’s parent hierarchy.

02 · Return restores the task

“Back to approval inbox” restores its filters, sort, page and scroll. It is not a blind history.back().

03 · Direct links still work

With no valid origin, show “Pay run overview”. Never invent a previous page or send the user outside Payobook.

04 · One control, one meaning

Breadcrumb = ancestor. Return = origin. Previous/next = record. Wizard steps = progress. Close = dismiss.

Research: what to borrow from enterprise products
Workday · Canvas breadcrumbs ↗

Documented pattern: secondary navigation, a non-clickable current location, and overflow for constrained width. Borrow clear location and accessible hidden ancestors. This is design-system evidence, not an audit of every Workday screen.

Oracle · Redwood Service Center ↗

Documented record navigation includes return to the list and movement to the next item. Borrow the preserved work queue and sibling navigation; do not turn every breadcrumb into history.

Salesforce · Lightning breadcrumbs ↗

Documented pattern: an ordered hierarchy with accessible navigation semantics. Borrow a consistent trail and explicit current-page treatment.

Lightning console navigation ↗ also documents workspace tabs, keyboard movement and close controls. This informs C, not a universal app-wide tab bar.

IBM · Carbon breadcrumb guidance ↗

Established v10 guidance: breadcrumbs supplement primary navigation; use progress indicators for multistep work. Borrow the separation of location and workflow. This reference is an older documented baseline.

Reviewed 26 October 2026. These sources support the patterns; the recommendation and visual treatments are original Payobook design judgments. Enterprise products vary by module and release. There is no universal rule that every screen needs both a breadcrumb and a back button.

Behavior specification, accessibility and Payobook fit

Current code evidence. Payobook’s shared hub exposes openHub, hubBack, goBack and HubBackChip. Its pb_back payload already carries destination, lens and context. This is a useful foundation; it does not prove that all screens restore filters, sorting, pagination, focus or scroll. The pay-run list already has status, period and division filters. Make their restoration an explicit contract.

Recommended production contract. A canonical route identifies domain, parent record and current record. A separately validated origin identifies the return action and its list state. Keep names and sensitive record data out of public URLs; recheck permissions on every arrival. Use same-application destinations, stable IDs and short-lived session state scoped to user, database and company. Revalidate tenant and record access before restoring. A missing or inaccessible origin falls back to the nearest permitted parent.

Consistent placement. Shared global header → location/return row → title and status → local tabs → content. Keep company and country in explicit context controls, not a false ancestor trail. Show the current record once as the title in B; A also includes it as plain current-page text. Use chevrons only as separators. Do not show an inactive Back control on root screens.

Interaction details. Browser Back/Forward should traverse meaningful routes, not keystrokes. Return restores the originating queue, while ancestor navigation opens the canonical parent. Previous/next stays inside the same result set and does not create a new workspace tab for every record. A wizard uses its own labelled previous step and leave guard; it is never represented as record ancestry. Escape dismisses overlays before it affects page navigation.

Unsaved changes. Every in-app exit, including ancestors, scenario switching and workspace close, offers Save & continue, Discard, or Keep editing. A failed production save must keep the user on the form. Cross-page browser exits need the application’s router guard plus beforeunload. The prototype uses local sample notes and a native browser leave warning; it performs no server save.

Accessible by construction. Named navigation landmarks; ordinary ancestor links; aria-current="page" on A’s current crumb; visible focus; explicit previous/next labels; native overflow disclosure; focus sent to the new heading after in-app navigation; status announcements; modal focus containment; 40px controls. C uses labelled open-record links with separate close buttons rather than claiming incomplete ARIA tab semantics. Validate production at 200% zoom, with screen readers, translated long names and touch.

Prototype coverage. All three concepts; parent and source navigation; restored status filter; review queue; record previous/next; workspace switching and closing; direct-link fallback; note save/discard/keep editing; browser history; 390px phone composition. All names and amounts are fictional. Search, approvals, permissions, real payroll writes and cross-session drafts are outside this concept.

Rollout and acceptance. First standardize the shared header and return payload. Pilot on pay run → payslip, inbox → payslip, people → contract and workforce → time off. Check no loops, stale origins or wrong-company returns; keyboard focus returns to the triggering row; a deleted/forbidden record has a safe parent; refresh preserves a valid route; filter/sort/page/scroll survive a round trip. Compare task completion and wrong turns with existing navigation before expanding. C requires a separate operator study.
