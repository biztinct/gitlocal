Payobook Learn

v2 Implementation Design — per-screen coaching, Pay Run first

The v1 strategy (three surfaces, one content spine) has since been implemented end-to-end for health19 as addons/health_learn, and the implementation taught us things the prototype could not. This document back-ports that proven architecture to Payobook and defines exactly what we build first: the Pay Run menu and all its sub-menus.

01
What changed since v1

v1 (this folder) proved the strategy. The health19 port (health19/docs/tutorial_crm → health19/addons/health_learn, 31 screens, 12 lessons, 8 missions, 32 intents, live in the product) proved the implementation — and made five decisions the v1 plan didn't have. v2 adopts all five.

v1 said

The Companion is one of three surfaces, opened from a hub/dock; delivery order Journey → Companion → Simulator; content in a future pb.learn.content model; anchors linted by a grep script; progress "per-user records" (unspecified); coach answers "grounded LLM".

v2 (as implemented in health_learn)

The Coach is always on, on every screen — a launcher + ? key opening a non-blocking drawer, mounted once in the web-client shell. Journey, Coach and missions ship together per menu section, screen by screen. Content = generated Odoo records (18 learn.* models) from the prototype via a generator + .po. Anchors = a JSON registry enforced by unit tests against real product templates. Progress/telemetry = server models (learn.progress, append-only learn.event, learn.confidence). Coach = deterministic retrieval with two declared LLM seams.
The v2 rule: coverage is per-screen, not per-surface. A menu item is "covered" when its screen has (a) anchors, (b) a Coach context + suggested intents, (c) a station on the Journey map with at least an outline, and (d) its risky actions taught with consequence cards. We ship the Pay Run section to that bar first, then repeat for the other sections.

Porting economics: health_learn's engine (engine/spotlight.js · runtime.js · screens.js · visuals.js, journey/, coach/ + coach_patch), its models, its generator (tools/gen_learn_data.py, 835 lines) and its test suite (7 files) are all product-agnostic by construction — content arrives as records, screens resolve via sidebar metadata, anchors via a registry. We port them near-verbatim and keep the learn.* model names identical so diffs against health_learn stay meaningful. What we re-derive is exactly what DESIGN_SPEC §8 lists: menus, anchors, worked example, risky actions, roles, terminology, brand.

02
The always-on Coach

The Coach is not a place you navigate to. Every in-scope screen gets a persistent "Stuck?" launcher (bottom-right) and the ? shortcut; both open a drawer grounded in the current screen.

Behaviour (per the health_learn implementation)

  • Mounted once, works everywhere. A CoachHost OWL component patched into the web client next to MainComponentsContainer (health_learn's coach_patch.js/xml pattern). Zero per-screen wiring — new screens get the Coach for free.
  • The drawer never dims or blocks the page. No backdrop, no focus trap; the screen behind stays clickable. The user reads the answer while doing the work. (Lessons are the one exception — there the spotlight card is the coaching, so the launcher hides.)
  • Screen resolution is metadata, not code. The Coach listens on ACTION_MANAGER:UI-UPDATED and resolves the active screen in three passes — action tag/xml_id → declared extra tags/xmlids → res_model — against matchers derived from the sidebar leaf. Payobook's pb.sidebar.item already carries exactly the needed fields (action_tag, match_action_tags, match_action_xmlids, match_models — pb_sidebar/data/pb_sidebar_data.xml), so learn.screen.sidebar_key points at a pb.sidebar.item xml-id and the matchers come from it.
  • Drawer anatomy (single template, used by both the live drawer and the Journey's demo dock — "do not fork it"): header "Grounded in this screen: <title>" → honesty banner → context card (YOU'RE ON: … + screen blurb) → Suggested for this screen chips → answers → composer.
  • Answer modes: Show me (sequenced highlight rings over real controls; if an anchor is not on this screen the Coach says so instead of flashing nothing), Simpler, Let me practise (hands off to the mission), Open lesson (when the screen's station has one).
  • Keyboard: ? toggles (ignored while typing), Esc closes drawer before modals. During a mission the step panel relocates rather than being buried (body.coach-open).

Payobook honesty banner

"I guide — you act. I never compute a run, approve a payslip or change a record for you." / "Tôi hướng dẫn — bạn thao tác. Tôi không bao giờ tự tính lương, phê duyệt phiếu lương hay sửa dữ liệu thay bạn."

Launcher coexistence (Payobook-specific)

Payobook's bottom-right corner is already occupied: the PayAI pill (pb_payroll_ai_insights) and, for demo users, the pb_coach "Getting Started" FAB. v2 rule: at most two floating controls, ever.

  • The Learn launcher replaces the pb_coach FAB in its slot (bottom-right, stacked above the PayAI pill). pb_coach's FAB remains only for demo-tenant users until Phase C (§9).
  • PayAI stays the data copilot (numbers, records, actions); the Coach is the learning surface (how/why/what-if). Each links to the other: the Coach's fallback offers "Ask PayAI about your data"; PayAI's system prompt gains a "how do I…" hand-off to the Coach (it already launches tours via the sanctioned action envelope — payroll_ai_engine.py:302-318).

Anchors: keep data-coach

health_learn introduced data-a; Payobook already has 40+ live data-coach anchors across 6 modules, referenced by pb_coach tours and PayAI. Decision: the registry attribute stays data-coach — the registry/tests/spotlight read one configurable attribute name, so the port is a one-line constant. Renaming would churn every template for zero behaviour.

static/src/anchors.json lists every anchor as {screen, file, desc, kind: product|pattern|practice} — pattern for per-record variants (e.g. t-attf-data-coach="pk-card-#{record.id}"), practice for fixture-only anchors. test_anchor_registry.py enforces all three directions: every registry entry exists in its template, every template anchor is registered, every content reference resolves.

Missions — the practice ladder (decided 2026-08-09)

Missions come in two kinds, forming a ladder every tenant climbs as far as its type allows: learn (lessons on real screens, read-only) → practise (fixture missions, isolated) → prove (a live capstone, demo tenant only).

  • Fixture missions are universal — including the demo tenant. Prospects practise on the JS fixture exactly like customers: they can fail safely, the seeded anomaly is always there (another user can't have "fixed" it), and random practice computes never dirty the shared demo world. Customer/production tenants get only this kind.
  • Live capstone missions (kind = live) exist only on the demo tenant, gated by the demo group. Steps validate real actions on real records — the upgraded guided-trial climax: consequence interception before a real Compute, a real run travelling the real approval chain. Collision answer: per-user division — each demo signup is assigned one of the 12 divisions as theirs for the capstone (the pb_demo generator already regenerates per division), so two prospects never fight over the same run.
  • Soft gate between rungs: the capstone card nudges "do the practice mission first" but does not hard-lock — an AE driving a live demo can jump straight to the climax. The gate can harden to a flag if demo hygiene demands it.

Phase A fixture missions (2 full + 1 outline)

  • m1 · Run the July pay run (full, confidence run +25): open wizard → choose Retail (wrong choice coached) → consequence interception before Compute (scope 48 drafts / reversible yes / verify import committed) → seeded anomaly: Trần Văn Hùng's OT at 282% of June — decision step where Accept as correct triggers recovery ("4.6h → 46h is a classic") → flag → submit → pipeline → debrief + pre-finalise checklist.
  • m2 · Review & approve like a manager (full, confidence approve +20): the run waiting at HR review → sample 3 slips + every flag → variance vs June → decision: approve vs reject; reject path requires the written reason (mirrors pb_reject_note) → undo step (a rejection is reversible; a Done run is not) → debrief.
  • m3 · Fix a bad import before it becomes salaries (outline): duplicate rows + one orphan employee; score drops; fix vs commit-anyway.

Phase B live capstone (demo only)

  • mL1 · Run your division's June payroll — for real: the pb_coach hero-tour climax re-expressed as a live mission on the user's assigned division: real consequence card → real Compute → open a real flagged payslip → submit → approve through level0/level1/level2 → Done. Debrief compares their run to the fixture rehearsal. Until this ships, the existing pb_coach hero tour keeps delivering the live climax — nothing regresses during Phase A.
Isolation stays testable in both directions: fixture missions keep health_learn's "never call a product method" test; live missions get the inverse — a test asserting kind=live content refuses to run unless the company is the demo tenant and the user is in the demo group.

Coach intelligence & AI seams

Deterministic retrieval first

Ported unchanged from learn_intent.py: diacritic-folding normaliser (EN+VI stop-words), scoring (exact 100+len · substring 40+2·len · reverse 20+len · loose overlap needs ≥2 topic words), +25 on-screen bonus, −5 for '*' intents, floor 20 else honest fallback (per-screen: "I don't have that — try a chip, or ask PayAI about your data"). Misses are logged as coach_miss events — the question-clustering input for new content.

The deny list (Payobook's "clinical markers")

health_learn refuses clinical questions before retrieval. Payobook's equivalent: tax/legal-advice markers ("giảm đóng BHXH", "khai thấp", "avoid tax", "under-declare", "trốn thuế"…) route to a fixed compliance intent — teach where the statutory rates live and who owns policy, never advise on minimising obligations.

Data boundaries — what leaves the server (audited 2026-08-09)

SystemSends to an external LLM?Detail (verified in code)
pb_coachNeverPure JS tours; no LLM, no network calls beyond one ORM read of res.users.login_date for first-run detection.
pb_learn (Phases A–C)NeverDeterministic retrieval over authored records; the bundle is served by your own Odoo. No provider is even configured.
pb_learn (Phase D _compose, off by default)Scrubbed question + authored corpus onlyThe prompt contains the user's question (regex-scrubbed of emails/phones/#ids/long numbers, 400-char cap) and the module's own teaching content — never a database record. That's a testable contract: the composer has no ORM access to payroll models. Residual risk: a person's name typed into the question survives regex scrubbing → mitigation below.
PayAI (existing)Yes — by designData queries fetch real records and embed them as JSON in the provider prompt (payroll_ai_engine.py:216-220). Most intents send aggregates (per-department totals/averages), but _query_individual_data (payroll_data_query.py:573-604) sends employee names, job titles and individual salaries (up to 20), and the query engine runs .sudo() throughout. Conversation history is also forwarded.
PayAI hardening (recommended, independent of pb_learn): (1) drop the .sudo() in payroll.data.query so answers respect the asking user's access rights — today a user without contract access can extract salaries through chat; (2) pseudonymise the individual path (send tokens, re-substitute names in the reply) or gate it to managers; (3) if data residency matters, a self-hosted provider slots into the existing factory. pb_learn's Phase D composer will reuse whatever provider policy PayAI lands on.

Two LLM seams, both optional

  1. _resolve_hook — may only choose an intent key from the scored candidates; it never authors text. Ships as a no-op.
  2. _compose — an LLM composer over the module's own corpus, for questions retrieval can't place. Payobook has a provider already: the PayAI engine (pb_payroll_ai_insights, OpenAI-backed). Same contract as health_learn: scrub the question (names, amounts, emails, phones; 400-char cap), corpus-capped prompt that forbids inventing rates/amounts and requires literal NO_ANSWER, discard empty/overlong replies, and badge the answer "Composed from the guide". Any failure → the deterministic fallback. Phase D, behind a config flag.

07
Honesty machinery

The health19 lesson: a tutorial rots silently unless drift has a price. Three enforcement layers, all ported.

1 · Contract checker — taught facts verified against source

tools/check_contract.py + contract.json: every teachable product fact is a checked entry {id, why, kind, file, expect, taughtIn}. Payobook's first contract (~12 checks):

  • Approval selection keys draft/level0/level1/level2/done and the level0-before-level1 insertion (pb_payruns/models/hr_payslip_run.py selection_add) — taught in L2, m2.
  • Rejection testimony fields pb_reject_note/uid/date exist and are readonly — taught in L2, m2.
  • The four security-group xmlids used by capability gating exist in pb_hr_payroll_base.
  • The 7 sidebar-leaf xmlids + action tags the screens resolve by (pb_sidebar_data.xml).
  • Done-state actions action_pb_bank_export/_journals/_payments exist — taught in L2.
  • Import wizard's 4-step flow + confidence surface exist — taught in L4.
  • PayAI's _KNOWN_TOURS whitelist matches what the Coach hands off to (until §9 retires it).
  • VI .po spot-checks: shipped sidebar labels the content quotes ("Chạy bảng lương"…).

2 · Anchor lint as unit tests

test_anchor_registry.py: registry ↔ templates ↔ content, three directions + no stray anchors. A PR that renames a button without updating the lesson step fails CI, not the learner.

3 · Token lint + generated-file discipline

Undeclared {{slots}} fail the build; every generated data file carries "GENERATED FILE. Do not edit. Source: docs/tutorial_poc/"; the generator's --check mode runs in CI so module data can never drift from the authored content.

Practice isolation is also a test: health_learn's test_12_missions_never_call_a_product_method pattern — Payobook missions run on the generated JS fixture and are structurally incapable of touching hr.payslip.

Decisions taken & open questions

All questions resolved in review, 2026-08-09.

  1. Model names stay learn.* (not pb.learn.*) — maximum diffability against health_learn; the products never share a DB.
  2. Anchor attribute stays data-coach — 40+ live anchors keep working; the engine reads a constant.
  3. The Learn launcher replaces pb_coach's FAB slot; PayAI pill unchanged; two floating controls maximum.
  4. Import wizard is a screen without a station — coached and anchored, walked by L4, absent from the map.
  5. The three ledgers share anchors (one template) but are three screens/stations — resolution by action tag makes this free.
  6. Authoring stays prototype-first (this folder) with the generator, exactly like health19 — not hand-written XML.
  7. The practice ladder (decided 2026-08-09): fixture missions are universal — customers and demo prospects alike practise on isolated JS data; live missions are demo-tenant-only (kind=live, demo-group gated, inverse isolation test), delivered as the Phase B capstone.
  8. Demo collisions → per-user division: each demo signup owns one of the 12 divisions for its capstone; the pb_demo generator regenerates per division.
  9. Live values in lesson/coach cards land in Phase B (whitelisted read-only resolver, static worked example as fallback); Phase A ships static content.
  10. Demo world adopts pb_learn in Phase A, coexisting with the pb_coach hero tour until the Phase B capstone replaces the climax and Phase C retires pb_coach.
  11. Journey placement (decided 2026-08-09): a leaf in the Pay Run section through Phases A–B; promoted to a top-level "Learn" section of its own once all sections are implemented (Phase C).
  12. Progress privacy (decided 2026-08-09): learn.progress / learn.confidence stay private + author-only, exactly as health_learn ships. No manager visibility.
  13. Data boundaries (decided 2026-08-09): pb_learn never sends database records to any LLM in any phase (§6 audit table); the Phase D composer sends only the scrubbed question + authored corpus, behind a flag that ships off. PayAI's existing data-egress and .sudo() issues are tracked as an independent hardening task (§6).

No open questions remain — the design is fully decided and ready for Phase A.
