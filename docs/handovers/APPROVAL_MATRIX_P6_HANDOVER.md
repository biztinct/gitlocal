## 1. Scope

**A. The eleven `biz.approval.chain.mixin` consumers run on the engine** (shim in `biz_approval_workflow`, adapters in each owning module):
1. `biz_approval_workflow` adds `models/chain_shim.py`: `_inherit = 'biz.approval.chain.mixin'` (the abstract mixin, so every consumer inherits it with no edits) implementing: `_approval_engine_process_key()` (from a per-model registry `CHAIN_PROCESS_KEYS` filled by the consumer modules' data, see §2 table), `_engine_managed()` (a published workflow exists for that key + the record's company), and overrides of `_advance_state`, `action_refuse_chain`, `_approval_can`, `_approval_can_refuse`, `get_approval_trail`, `_approval_widget_payload`, `write`. Semantics when managed: `_advance_state(first forward state)` from the initial state = **submit** (engine request created; the consumer's state moves to its first intermediate state, e.g. `submitted`, through `_chain_state_write` so existing views keep working); `_advance_state(any later state)` = **approve the active step** as the caller (engine `decide`), and when the engine reports the step done it moves the consumer's state to the next intermediate state (mapping table per model, §2); final engine `applied` → `_chain_state_write(final_state)` + `_before/_after_approval_transition(final_state)` exactly as today; `action_refuse_chain(note)` = engine `reject`; reverse pairs in `pb_pay` (`proposed→draft` etc.) = engine `return`. Direct `_chain_state_write` callers (cancel / withdraw / reset / undo) → the shim's `write` detects a managed open request and **cancels it with a reason** ("Cancelled from the record: <state>") so no request is orphaned; the six sites are listed in §2 — no edits needed there, but each gets a test. Unmanaged (no published workflow) → class-dict behaviour unchanged.
2. Each consumer module gets: `_approval_process_key`, `_approval_context` (company, scope `division:<id>` of the employee's department on the record date, `kind_key` where natural, facts and amount, makers = `create_uid` + the employee's user, subjects = employee's user), `_approval_capabilities`, `_approval_coverage_scopes` (divisions), `_approval_manager_uids` (employee.parent_id), and the state mapping. Existing form buttons stay but are driven by the shim; add the engine route widget (`biz_approval_stepper` fed from the request trail) to each form; the inbox shows all of them with the right icon and amount.
3. Catalogue split (edit `pb_approval_config/data/processes.xml`): `assets`, `correction`, `bankchange` (new: Bank account change), `trip`, `awards` (= `pb.incentive`), `recognition` (new: `pb.rnr.nomination`), `extension` (new: Contract extension), `master` (= `pb.profile.change.request`), `resign`, `paychange` (= `pb.pay.change`), `payreview` (new: Pay review). One model per process key.
4. Default workflow per process per company = today's ladder translated to roles/manager (§2 table), published; new roles seeded: `equipment` (Equipment team), `pay_head` (Head of pay), `lifecycle` (HR lifecycle team); responsibilities from today's group holders (first holder = person, second = backup).

**B. Leave, overtime** (`pb_timeoff`, `pb_hr_workforce`):
5. `hr.leave` adapter (in `pb_timeoff`, key `leave`): submit on `action_confirm`/create-at-confirm; facts `days`, `leave_type`, `is_unpaid`, `overlaps_payroll_cutoff`; manager mode default (Their manager → HR lead); `_approval_apply` = `action_approve` as the final approver (hr_holidays folds first/second validation; if the approver lacks the holidays group, block with the message and offer reassignment); reject → `action_refuse`; return = `action_refuse` + note "Sent back: …" then the employee re-confirms. `pb.timeoff.act` and the standard `hr.leave` buttons route through the engine when managed.
6. `hr.overtime.request` adapter (key `overtime`, `pb_hr_workforce`): `action_submit` → engine submit (keep the sealed-fields rail); `action_approve`/`action_refuse` → engine decide when managed; `_approval_apply` = the existing approve body (recompute split via `pb.ot.ceiling._split`, write sealed fields through `_ot_chain()`); facts `hours`, `ot_type`, `year_to_date_hours` (for the 200 h/yr condition), `over_ceiling` (bool). Grid `approve_requests` routes through the engine. P4's packet still submits OT the same way.
7. `hr.attendance.correction` is a chain consumer (A). 

**C. One inbox for teams; retire `pb_team` and the Workforce approvals lens** (`pb_mission`, `pb_hub`, `pb_team`):
8. `pb.approval.inbox.list_requests` gains `scope='team'` (requests whose subject employee is in `_my_team(recursive=True)` of the caller, computed the pb_team way) and `scope='org'` for HR/org approvers. `pb_mission`'s `approvals` lens mounts `PbInbox` with `scope: 'team'` (edit LENSES :173-176, components :200, template :129-131, label :451, `onDockQueue` :290, import :56); `pb_dock.js` reads its queue from `pb.approval.inbox` (`MODEL` :40, approve/refuse at :454-475 → `decide`). `pb_team` becomes a shell module (manifest bumped, models removed, action tag `pb_team` → redirect JS to Workforce lens `approvals`); `pb_mission` drops the `pb_team` dependency; palette row `wf_approvals` (`hub_palette_entries.js:158-160`) points at the Workforce lens and keeps the label "Team Approvals".

**D. Role grants, hand-overs and support access** (`biz_access` adds depends `biz_approval_workflow`; `pb_tenancy` likewise):
9. New `pb.access.request` (stored, `biz_access`): `kind` grant/remove/delegate, `profile_ids`, `target_user_id`, `delegate_user_id`, `date_start/end`, `reason`, `requested_by`, `state` via engine (key `roles`). `pb.access.grant/remove/delegate` create a request and submit; `_approval_apply` performs the existing body (grant/remove/delegate as the final approver, who must hold `group_access_manager`; else block + reassign). Fast lane → immediate as today. Access board JS shows "Sent for approval" + door; the History tab lists them. Default seed: Access team (review) → Tenant administrator (approve); with the tenant-admin role's holder as responsibility. Approval delegation (engine hand-overs) and access hand-overs stay separate concepts; the People & backups screen links to the Access board for role questions.
10. `pb.support.access` (`pb_tenancy`): `issue()` creates the row in `issued` **and** an engine request (key `support`; facts `minutes`, `support_name`, `reason`); `claim()` refuses unless the request is `applied` ("Support access has not been approved yet"); `_approval_apply` = mark `approved_at`; reject → `refused` with `refused_reason` (the state that had no path). Default seed: Tenant administrator. Fast lane allowed (owner ruling) — the tenant may publish it.

**E. Cross-cutting**: audit entries for applied grants; catalogue rows connected; seeds; VI `.po`; tests; Chrome (local); deploy checklist.

**Non-goals:** setup & rules processes (statutory tables, pay bands, FX, scheme map, mappings), platform tenant operations, probation/PIP verdicts, letters, new hire, unlock-a-day, spreadsheet import (all P7).

## 3. Safety rails
1. When a workflow is published for a type, no legacy button can skip a step; when none is published, behaviour is exactly today's (the shim is dormant). Seeds publish defaults on install so the shim is live from day one; a company may replace them with the fast lane.
2. Every cancel/withdraw/reset/undo path closes the open request with a logged reason; no request may stay `pending` on a record that left the chain.
3. `pb.pay.change.action_apply` remains a separate manual step after `approved` (it writes wages); it is not part of the request.
4. Leave approval as the final approver must hold the holidays group; otherwise block + reassign. Same for overtime deciders and access managers.
5. The team scope must never reveal requests outside the caller's team unless `_is_hr()`/org approver.
