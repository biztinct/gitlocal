**Handover from Fable (design) to Opus (build) · read `APPROVAL_MATRIX_LEDGER.md` first (AM1–AM17+) and append. Phases 1–3 are merged locally (engine, Matrix + inbox, pay runs on the engine). Read their reports in the ledger and the code before starting.**

## 1. Scope

**A. Weekly timesheet packet** (new module `pb_timesheet_approval`, depends `pb_hr_workforce, pb_attendance_flow, pb_close, biz_approval_workflow, pb_approval_config, pb_workforce_payroll_bridge`):
1. A durable record `pb.timesheet.packet`: one per employee × week (company, week_start, employee, attempt). Built from the employee's `hr.attendance` rows in that week (all `pb_entry_source` values: grid, device, import, correction) and the week's `hr.overtime.request` rows. Stores a per-day snapshot (`days_json`: date, reg hours, OT by type with request ids and states, source ids), totals (`reg_hours`, `ot_hours` by type, `bonus_hours`, `total_hours`), `source_hash` (sha256 over sorted attendance ids + check_in/out + OT ids + hours), `state` via the engine request, `approved_hash`, `packet_note`.
2. Adapter (`_approval_process_key = 'timesheet'`): scope keys `division:<id>`, `` (division via `pb.division.division_for(employee.department_id, week_start)`); `kind_key = 'week'`; facts: `total_hours`, `ot_hours`, `reg_hours`, `days_with_hours` (int), `has_overtime` (bool), `variance_vs_schedule_pct` (vs `resource_calendar` hours), `late_submission` (bool: after the company's cut-off day); makers = users who created the source rows (device rows have none) + the submitter; subjects = the employee's user; `_approval_manager_uids` = `employee.parent_id.user_id` (manager mode is the default route: **Their manager → HR lead**); evidence: none required by default; `_approval_apply` = mark packet approved with `approved_hash`, and **submit the week's draft OT requests through their own adapter/legacy actions as the approving manager** so approved OT stays consistent (do not double-approve already approved OT); `_approval_return` = packet back to draft with note.
3. Grid integration (`hr.attendance.weekentry` RPCs + `attendance_weekgrid.js`): a **Submit week** action per employee row and a bulk one per department (creates/refreshes packets, submits them — `submit_week` today only bulk-submits OT; extend it: OT submission stays, packet submission is added). Per-row status chip (Draft / Waiting for <name> / Approved / Returned) and a door to the request in the inbox. Editing a day whose packet is pending or approved is refused with "This week is with <name> for approval. Send it back to change it." (a returned/none packet is editable). `pb_close` locking stays as is; a locked day cannot be resubmitted.
4. Inbox card for `timesheet` (icon `clock`, "44.5 h incl. 4.5 h overtime", employee, week, division); the drawer shows the per-day snapshot as a small 7-column table and the OT chips.
5. Payroll prerequisite: a per-company setting `Payroll reads approved timesheets` (default **on** since no payroll is live) with two effects: (a) the pay run wizard's exception panel lists employees in the run period with weeks that have no approved packet (advisory lines via `pb_close`'s `_close_append_exceptions` pattern) and a company option `Block the run until every week is approved` (default off); (b) a new input-source rung in `_get_formula_input_values` (bridge module) filling hour codes from **approved packets only**: `REGHRS` (sum reg hours in period), `WORKDAYS` (days with hours), `TOTHRS`, and — when the setting is on — the existing `OTHRS150/200/300/NGT` and `BONHRS` codes are read from the packets' approved OT snapshot instead of live OT requests (values equal by construction; provenance says "Approved timesheet · week of …"). Unresolved (no approved packet) → the input stays unresolved and the existing provenance chain shows why.
6. Late policy: the company cut-off day comes from the blueprint calendar (`pb_blueprint` `calendar_json` → `cutoff_day`) when present, else day 15; `late_submission` is a fact the workflow can condition on ("Only when submitted after the cut-off → HR lead").
7. Default workflow seed per company: "Weekly timesheet" = Their manager (review) → HR lead (approve), published as the company default; plus the `timesheet` process row switched to connected.

**B. Scheme-change proposals** (in `pb_hr_payroll_formula` + `pb_formula_studio`, add depends `biz_approval_workflow, pb_approval_config`):
8. New model `pb.scheme.proposal` (in `pb_hr_payroll_formula`): `config_id` (the scheme being changed), `kind` ∈ `activate | merge | release | rollback | archive`, `branch_id` (for merge), `release_id` (for rollback), `from_milestone_id`, `sealed_hash` (= `_evidence_hash` of the candidate content: the branch for merge, the config itself for activate/release, the pre-rollback target for rollback), `diff_json` (from `_branch_diff_rows` / `_changes_between_ver`), `test_summary_json` (latest sample-test / shadow-run results), `state` via the engine request (`pending/approved/applied/returned/rejected`), `applied_at`, `applied_release_id`. Adapter (`_approval_process_key = 'scheme_change'`): scope keys `scheme:<config id>`, ``; `kind_key = kind`; facts: `rules_changed` (int), `payslips_per_month` (int, from the last run of that config), `tests_passed` (bool), `has_shadow_run` (bool), `touches_tax` (bool: any changed rule with a statutory/tax category), `kind`; makers = the branch/rule editors (`hr.formula.rule.version.user_id` in the candidate range) + submitter; `_approval_apply` = re-verify `sealed_hash` against current content, then perform the kind: `activate` → `action_activate` body; `merge` → `branch_merge` body then seal a release with `state='approved'`; `release` → `release_approve` body; `rollback` → `rollback_apply` body; `archive` → `action_archive`. Hash mismatch → apply refused: "The scheme changed after this proposal was sent. Send it back and propose again."
9. **Gate the four doors** (`formula_config.action_activate` :1082, `pb_formula_studio.branch_merge` :3823, `release_approve` :2966, `rollback_apply` :3143, plus `action_archive` :1097 and `_cfg_run` :11975): each becomes `_require_applied_proposal(config, kind)` — they run only from `_approval_apply` of a proposal in `approved` state (context token pattern like `_CHAIN_WRITE_TOKEN`), unless the company has **no published `scheme_change` workflow** or that workflow is the fast lane (then the door proposes-and-applies in one step, logged as `applied` with the fast-lane confirmation). The studio buttons become **Propose for approval** (activate), **Propose merge**, **Propose release**, **Propose rollback**, each opening a small confirm sheet (what changes, tests summary, note) and creating the proposal; the config header shows a status chip with a door to the request.
10. **Isolate edits on an active scheme**: `hr.formula.rule.write` (formula_rule.py:1669 override) and `hr.formula.config.write` for rule-bearing fields refuse when `config.state == 'active'` and the company has scheme-change approval in force, with "This scheme is live. Create a branch, make the change there, then propose it." (the studio's editor already knows branches: `branch_create` :3780). Branch edits are free. Imports/bulk edits into an active config route the same way.
11. **Provenance on payslips**: stamp `formula_milestone_id` and `formula_content_hash` on `hr.payslip` at compute time (hr_payslip_formula.py compute paths :151/:1076), so a run records exactly which sealed content computed it; the run's inbox card and the Explorer can show "Scheme content v14".
12. `hr.formula.release` gets `state` (`approved` default for existing rows via migration; new rows come from proposals) and `proposal_id`. The public client review link stays acknowledgement-only (it never satisfies a seat) — its sign-off becomes evidence on the proposal ("Client acknowledged on the review link").
13. Blueprint: the Connect card's second line (Scheme change approval) now reads the real binding; Finish's "activate later" advice points at "Propose for approval". Blueprint never activates (unchanged).
14. Default workflow seed per company: "Scheme change" = Scheme owner (review) → Payroll manager (approve) → Country director (final), published as the company default; `scheme_change` process row connected.
15. VI `.po`, tests, Chrome validation (local), deploy checklist.

**Non-goals:** leave/overtime/attendance-correction adapters (P5 — OT approval stays its own logic; the packet only *submits* OT), project timesheets (none exist), money-out/pay-data adapters (P5).

## 3. Safety rails
1. Payroll must never read hours from an unapproved packet when the setting is on; provenance names the packet.
2. Nothing in this phase changes OT ceilings, bonus-hour splitting or leave rules; the packet snapshots what those modules decided.
3. A pending or approved packet freezes its week in the grid; a returned one thaws it. Locked days are never editable regardless.
4. No door to activate/merge/release/rollback a scheme exists outside a proposal, except the fast lane by published choice.
5. `sealed_hash` must match at apply time; otherwise refuse and explain.
6. Client review sign-off is evidence only.
7. No `sudo()` to apply; the applying user is the final approver (re-check rights on the config).
